Large JSON responses hold the whole payload in memory. They don't have to.

A tiny streaming serializer for large collections — one API in six languages, with byte-for-byte identical output across Go, Rust, Python, Node, .NET, and Java.

This started with a pager alert, the way these things usually do.

We had an endpoint that returned a list. Most days the list was a few hundred rows and nobody thought about it. Then a customer with a lot of data hit it, the list was ~50,000 rows, and the service fell over — not because the query was slow, not because the network was slow, but because the handler built the entire response as one giant object in memory before a single byte went out the door. Multiply that by a handful of concurrent requests and the pod hit its memory limit and got killed.

The fix in the moment was the usual one: a paginated endpoint, a LIMIT, a stern comment. But it nagged at me, because the shape of the bug is everywhere. Almost every web service, in almost every language, serializes and deserializes large object graphs on hot paths, and the idiomatic way to do it — json.dumps(...), JSON.stringify(...), JsonSerializer.Serialize(...) — holds several multiples of the payload in memory during a single operation. The whole thing becomes one big string before it reaches the socket. Under load that compounds: N requests, each holding a full copy.

The annoying part is that the streaming primitive already exists in every ecosystem. Python has ijson. Node has stream-json. .NET has DeserializeAsyncEnumerable. Go has json.Decoder. Rust has serde_json::StreamDeserializer. Java has Jackson's streaming parser. The tools are there. They're just fiddly enough, and different enough per language, that nobody reaches for them until after the incident.

So I set out to build the thing I wished existed: one tiny, identical API for streaming a large collection element-by-element, in every language I work in. I called it flatwire, because the goal is a flat memory profile over the wire.

The one idea

The whole library is basically one sentence: stream a large collection one element at a time, so peak memory is bounded by the largest single element instead of the size of the whole collection.

On encode, each element is written straight to the output stream and then dropped — you never hold the full array. On decode, the reader finds element boundaries and hands you one element at a time, so the whole array is never resident at once.

The surface is deliberately small — two functions do the real work:

import flatwire

# stream a huge collection out; peak memory is one element, not the whole list
with open("out.json", "wb") as fp:
    flatwire.encode_array(rows, fp)

# read it back lazily
with open("out.json", "rb") as fp:
    for row in flatwire.decode_array(fp):
        handle(row)

That's it. The same pair exists in Node (encodeArray/decodeArray), .NET (Flat.EncodeArray/DecodeArray), Rust, Go, and Java, with names that fit each language's conventions.

The numbers, and the honest part

Here's what "memory flat" means, measured encoding arrays of records:

Payload                  stdlib encode      flatwire encode
──────────────────────────────────────────────────────────
~2.5 MB   (10k records)   5.1 MB peak        1.4 KB peak
~12.7 MB  (50k records)  25.5 MB peak        1.4 KB peak

Encode memory is flat at ~1.4 KB whether the payload is a quarter-megabyte or thirteen megabytes. Decode holds a fixed ~200 KB working buffer regardless of size — about a 99.5% reduction at 50k rows.

Now the part I want to be straight about, because it's the part a good reviewer will poke at first: flatwire is not trying to beat your fastest serializer on raw throughput. If you compare against an optimized C extension like orjson, flatwire still trades some CPU for flat memory. But here's where I have to tell on myself: when I first shipped this, that trade was brutal in Python — streaming-and-discarding a 12 MB array was roughly 30× slower than json.loads, because my Python decoder was a hand-written, character-by-character scanner running in the interpreter. Every other language wrapped a native/compiled parser and paid ~1–2×; Python alone was eating an order-of-magnitude tax.

That bugged me enough that I went back and fixed it in 1.1.0. The insight was embarrassingly simple: I didn't need to hand-scan bytes at all. Python's standard library already ships a C-accelerated JSON parser, and its JSONDecoder.raw_decode will parse exactly one value starting at a given offset and tell you where it stopped. So I rewrote the decode loop to lean on that — skip whitespace, raw_decode one element, advance, yield, repeat — instead of walking characters myself. Same streaming behavior, same chunk-boundary handling, same flat memory, but the hot loop is now C.

On the same 12 MB array, streaming decode went from ~2.7 s to ~0.17 s — from ~30× down to about 2.2× of json.loads — with no new dependency. Encode got an optional lane too: pip install flatwire[fast] routes per-element encoding through orjson when it's present (~1.5× a bulk orjson.dumps), while the default install stays zero-dependency.

Here's the honest, updated picture — streaming and discarding a 12 MB array, per language, relative to that language's native materialize-then-iterate:

Language   Native decoder used           flatwire streaming decode
────────────────────────────────────────────────────────────────
Go         encoding/json                 ~0.9x   (faster — never builds the list)
.NET       DeserializeAsyncEnumerable    ~1x
Java       Jackson streaming             ~1.1x
Rust       compiled serde_json scanner   ~1.8x
Python     stdlib raw_decode (C)         ~2.2x   (was ~30x)
Node       V8 JSON.parse per element     ~5.4x

And the memory side, which never changed because it was the point all along:

Approach (Python, 12.7 MB array)      Peak memory    Relative time
──────────────────────────────────────────────────────────────────
json     (materialize, then iterate)   36.5 MB        1x
orjson   (materialize, then iterate)   170.5 MB       ~0.65x
flatwire (stream, discard)             ~200 KB        ~2.2x

So the pitch still isn't "throw away orjson." It's: use orjson when the whole collection fits comfortably in memory and you want peak speed; use flatwire when the collection is large and memory is the constraint — and now you pay ~2× for that flat profile in Python, not 30×. Different tool, different job — but I'm a lot happier defending that 2× in a code review than I was defending 30×.

The number that actually changed how I think about this, though, wasn't peak memory — it was time-to-first-row. A handler that materializes the whole response can't emit row 0 until it has built the entire payload, so its time-to-first-byte scales with size: ~490 ms at 10k rows, ~2.8 s at 50k. Streaming emits row 0 in about a millisecond, flat. That's the difference between a UI that feels instant and one that spins. And under concurrency it compounds: 32 concurrent decodes of a 20k-row payload used 266 MB materialized versus 4.1 MB streaming. Flat peak-per-request is exactly why p99 latency stops cliff-diving when traffic spikes.

Why do it six times? (This is the actually-interesting part.)

Here's the thing I didn't expect. Once you decide to wrap "the streaming primitive" in six languages, the wrapping is commodity — any senior engineer can do it in an afternoon per language. What's not commodity is making the six agree.

flatwire also speaks three more wire formats behind the same format= selector: XML, binary MessagePack, and binary CBOR. And for the two binary formats I made a much stronger promise than "it round-trips" — I promised byte-identical output across all six languages. The exact same value encodes to the exact same bytes whether you run it in Go or Rust or Node.

That promise is where all the actual engineering went, because the naive implementations do not agree. A few of the potholes:

  • Integer encoding. MessagePack and CBOR both let you encode the number 42 several legal ways. To get byte-identity you have to pick a canonical rule — shortest encoding that fits, non-negative uses unsigned, negative uses signed — and enforce it everywhere. Miss it in one language and the bytes diverge.
  • Map key order. JSON objects and hash maps iterate in whatever order the language feels like. If you want identical bytes you have to sort keys by their UTF-8 byte sequence — and "sort by UTF-8 bytes" is subtly not the same as Java's default String comparison (which is UTF-16 based and differs on characters outside the basic plane). That one cost me an afternoon.
  • Floats. Always encode as 64-bit IEEE-754, no clever shortening, or the bytes wander.
  • A JavaScript gotcha. 1e300 is an integer-valued Number in JS, but it is emphatically not a 64-bit int, and if you route it through the integer path it corrupts. The fix is checking Number.isSafeInteger, not Number.isInteger.

The only way I trusted any of this was to stop hand-waving and prove it. So there's a shared corpus of JSON fixtures — Unicode edge cases, deep nesting, huge numbers, empty arrays, tricky escapes — and a conformance runner that pushes that corpus through all six languages on every push to CI, then diffs the encoded bytes. The result is a published matrix: 10/10 of the byte-identical-tier cases are byte-identical across all six runtimes, for both MessagePack and CBOR. That test suite caught four real bugs I'd otherwise have shipped, including the 1e300 one and a .NET type-coercion issue in the runner itself.

That's the part I'm proud of. It turns "six wrappers" into "one spec, six conforming implementations." A stream written by a Go service decodes to the same value — and, for the binary formats, from the same bytes — in a browser, a .NET worker, or a Python job. No schema registry, no IDL.

The bytes are the contract.

The stuff that makes it real instead of a toy

A streaming primitive is a nice demo. What makes it usable in production is the boring surrounding work, and honestly this is where most "I built a library" projects stop and shouldn't:

  • Partial-stream failure semantics. The unspoken problem with streaming a response: you've already sent 200 OK and half the array when element 40,000 throws. A bare streamed array gives the client no way to tell "finished cleanly" from "the connection died" from "the producer errored after N rows." flatwire wraps the stream in a small envelope whose terminal status is written last, so the consumer can distinguish all three — clean completion, an in-band error with details, or truncation. It's plain JSON, so it interoperates across all six languages.
  • Backpressure. Streaming without honoring the writer's backpressure just moves the memory from your heap into the socket buffer — you haven't actually fixed anything. The encoders wait on the drain signal so a slow consumer throttles the producer instead of ballooning memory.
  • Framework adapters. The adoption moment isn't encode_array(items, fp); it's return StreamingResponse(...) in one line in FastAPI, or sendArray(res, rows) in Express, and the endpoint just stops OOM-ing. Those one-liners exist for all six languages now.
  • A CLI. flatwire cat, flatwire convert, flatwire stats — stream and convert files of any size in constant memory, because sometimes you just want to poke at a 5 GB file without loading it.

What I'd tell you if you were about to build this

Three things I actually took away:

  1. The technique is rarely the moat. Every ecosystem already had the streaming primitive. The differentiator turned out to be the cross-language contract and the conformance suite that proves it — not the wrapping. If I'd stopped at "it streams," it wouldn't have been worth publishing.
  2. Write the honest baseline into the README — then go fix the thing you're apologizing for. The fastest way to lose a reader's trust is to overclaim. My first README said plainly "we're ~30× slower in Python but use 99.5% less memory, here's when to pick which" — and being that honest is what made the rest of the claims believable. But writing the weakness down also made it impossible to ignore, and a release later I'd turned that 30× into ~2× by leaning on the stdlib's C parser instead of my own scanner. The honesty came first; the fix came because of it.
  3. Prove the scary invariant in CI or it isn't true. "Byte-identical across six languages" is a sentence anyone can write. It's only real because a machine re-checks it on every commit against a corpus designed to break it.

flatwire is 1.1.0, Apache-2.0, and published to PyPI, npm, crates.io, NuGet, Maven Central, and Go. There's a live benchmark dashboard and a browser playground where you can paste a JSON array and watch it encode to all four formats with a size comparison.

If you've ever had a list endpoint quietly become a memory bomb, take a look — and if you find a case where the six languages don't produce identical bytes, please open an issue. That's exactly the bug I most want to hear about.
